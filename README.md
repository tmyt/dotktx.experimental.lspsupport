# DotKtX.Experimental.LspSupport

Experimental completion support for editing [DotKt](https://github.com/tmyt/dotkt)
projects with JetBrains' Kotlin language server.

The official language server cannot currently load DotKt's frontend KLIBs.
This package adds an incremental MSBuild target that:

1. depends on DotKt's public `DotKtResolveKlibReferences` target and reads the
   reference KLIB set it publishes as `@(DotKtResolvedKlibReference)`;
2. projects every referenced CLR declaration into an analysis-only JAR whose
   classfiles carry the Kotlin metadata they were declared with;
3. projects DotKt's own CLR standard library the same way, so `kotlin.clr` and the
   rest of the Kotlin API come from DotKt rather than from a JVM approximation;
4. writes the generated model below `.dotkt/lsp`; and
5. writes a `workspace.json` model understood by the language server's JSON
   workspace importer.

No Gradle project or Gradle wrapper is generated. `dotnet build` remains the
authority for compilation and diagnostics.

## Usage

Add the package as a private, build-only dependency:

```xml
<ItemGroup>
  <PackageReference
    Include="DotKtX.Experimental.LspSupport"
    Version="0.9.6"
    PrivateAssets="all"
    IncludeAssets="build" />
</ItemGroup>
```

This package targets DotKt SDK `0.9.23`. LspSupport versions are released
independently of the compiler version.

Add the generated root model to `.gitignore`:

```gitignore
.dotkt/
workspace.json
```

Run the normal build once:

```bash
dotnet build
```

Then open the project directory in VS Code with the official **Kotlin by
JetBrains** extension. If the extension has a forced build tool setting, set
`intellij.buildTool` to `json` or return it to its automatic default.

## Generated files

```text
workspace.json             JetBrains LSP project model
.dotkt/
└─ lsp/
   ├─ .stamp               MSBuild incremental output
   ├─ README.md
   ├─ projection-report.md what was kept, approximated and dropped
   └─ libraries/
      └─ dotkt-klib-java-stubs.jar
```

The package removes `.dotkt/**/*.kt` from DotKt's `@(KotlinCompile)` item so
the editor projection cannot enter the real CLR assembly. It refuses to
overwrite an existing `workspace.json` unless that file was generated by this
package.

The only analysis archive this package ships is `kotlin-builtins.jar`, which carries the
`*.kotlin_builtins` resources describing Kotlin's core classifiers - `Any`, `Int`,
`List` and the rest. The JVM maps these classifiers onto `java.lang` types and
primitives. The archive also includes `kotlin/Unit.class` and `kotlin/Function.class`:
the JVM analyzer needs Unit in callback type arguments and Function as the superclass of FunctionN.
No JVM-only stdlib functions are included. Every other
declaration is generated per project from DotKt's KLIBs without invoking `javac`.

Set `DotKtxExperimentalLspSupportEnabled` to `false` to disable generation.
`dotnet clean` removes the generated workspace when it is owned by this
package.

## Analysis model and known approximations

JetBrains LSP cannot consume a KLIB directly, so DotKt's standard library is
projected into the same analysis JAR as the CLR references. The builtins archive
also retains `Unit.class` and `Function.class`: callbacks need Unit in their
type arguments, and calling `(String) -> Unit` needs Function as the superclass
of Function1. These analysis-only ABI classes come from the compiler
distribution; the full JVM standard library is not included. DotKt 0.9.14
publishes its path as `$(DotKtStdlib)`. `kotlin.clr` -
`ClrRef`, `byref`, `StackBuffer`, `Span`, `stackBuffer`, `ClrEvent`, `clrEvent`,
`EventSubscription` and the rest - therefore comes from DotKt itself and needs no
hand-maintained overlay, and JVM-only APIs such as `kotlin.concurrent.thread` or
the `java.io.File` extensions never reach completion because they are not in
DotKt's standard library.

Nullability, declaration-site variance, extension receivers and two overloads
that differ only in nullability cannot be represented in Kotlin source or in a
plain Java classfile. Every referenced declaration is therefore emitted as a
minimal JVM classfile that carries the same `kotlin.Metadata` annotation a
compiled Kotlin library would, so the editor reads the CLR API as declared
instead of an approximation of it. Overloads that collide after JVM erasure keep
both declarations: the Kotlin name lives in the metadata and only the JVM name
is mangled.

Receiver function types also keep their `kotlin.ExtensionFunctionType` marker.
For example, a `configure: TextBlock.() -> Unit` parameter supplies an implicit
`this` inside the lambda, whereas `(TextBlock) -> Unit` supplies `it`. The marker
is retained inside generic arguments and nullable function types as well.

Suspend function types retain their `Type.flags` too. Without `SUSPEND_TYPE`,
`suspend CoroutineScope.() -> T` would appear as
`CoroutineScope.(Continuation<T>) -> Any?`, breaking coroutine context and return
type inference even though the real DotKt program compiles and runs.

This is what makes DotKt 0.9.14's nullability visible. That release annotates the
KLIB from the CLR's own nullable metadata, so `Exception.InnerException` arrives
as `Exception?` and `Exception.Message` as a non-null `String`, and only members
from assemblies without nullable annotations stay platform types. A plain Java
classfile would flatten all three into one.

Narrow or change that with `DotKtxExperimentalLspJavaProjection`, a
`;`-separated policy of `type:<fqn>`, `package:<prefix>`, `library:<name>`,
`all`, `no-supertype-closure`, `strict` and `no-metadata`:

```bash
dotnet build -p:DotKtxExperimentalLspJavaProjection="package:System.Text%3Bno-metadata"
```

`no-metadata` falls back to plain Java classfiles. That representation still
gives platform types for every reference type, but it cannot express exact
nullability, extension members or erasure-colliding overloads, and the
projection report counts everything it has to drop.

Everything the projection approximates or drops is counted in
`.dotkt/lsp/projection-report.md`, including generic overloads that collide
after JVM erasure, extension members that have no plain-Java shape, and
declaration-site variance that Java signatures cannot carry.

Top-level callables have no owning class on the JVM, so they are emitted as file
facade classes named by a `META-INF/*.kotlin_module` mapping, exactly as the
Kotlin compiler does. CLR attributes become JVM annotation interfaces; a Kotlin
annotation class has one constructor where a CLR attribute has overloads, so its
members become that single parameter list and the overloads it could not express
are counted.

The report separates what it lost into two kinds. *Upstream gaps* are absences in
the KLIB itself; none are reported against DotKt 0.9.14. *Representation
limits* are constructs Kotlin has no shape for at all. The remaining limit is CLR
attribute constructor overloads, because a Kotlin annotation class has exactly one
constructor. Neither category is silent. C# extension methods remain callable both
as declaring-class statics and as Kotlin extensions; the report counts that shape,
but it is not a loss or duplicate within one completion scope.

JVM-only stdlib APIs do not appear because the standard library declarations come
from DotKt's CLR KLIB. The analysis JARs are editor inputs only and must not be used
as DotKt compiler or runtime inputs.

The generated workspace also enables
`-Xcompanion-blocks` for LSP analysis. The serialized compiler arguments also
enable `companionBlocks` explicitly. Kotlin 2.4 hosts use the older
`companionBlocksAndExtensions` name, so the model retains that setting for
compatibility. DotKt provides this feature as an intrinsic CLR target capability; the generic JVM analysis
host has no equivalent target hook, so the analysis-only workspace supplies
the corresponding language flag explicitly. The old
`-XXLanguage:+CompanionBlocksAndExtensions` spelling does not enable companion
blocks in newer LSP hosts, where the language feature was split and renamed.

## Development

This is an original C# MSBuild integration tool, rather than a port of a Kotlin MPP
library. It follows the shared porting layout with a `.csproj` using
`Microsoft.NET.Sdk` and `OutputType=Exe`; `commonMain`, `clrMain`, `DotKtCommon`
and the MPP SDK do not apply. The Kotlin projects under `tests/` are consumers and
fixtures built with `DotKt.Sdk`, pinned to `0.9.23` in `global.json`. The toolchain
and CLR standard library use DotKt `0.9.23` / Kotlin `2.4.21`.

```text
src/DotKtX.Experimental.LspSupport/
  DotKtX.Experimental.LspSupport.csproj
  *.cs, *.proto                     Generator and metadata schemas
  packaging/
    DotKtX.Experimental.LspSupport.nuspec
    build/                          Consumer MSBuild props and targets
tests/
  Smoke/                            Executable consumer and LSP checks
  ReceiverFixture/                  Receiver and suspend callback library
scripts/                            Build, verification and packaging
docs/                               Implementation notes
tools/kotlin-metadata-reference/    Development-only metadata probes
upstream/                           Optional, ignored reference clones
artifacts/
  bin/<project>/<configuration>/<tfm>/
  obj/<project>/
  packages/
  verification/                     Logs and actual stdout
```

Prerequisites: .NET 10 SDK, a JDK providing `java`, `jar` and `javap`, Node.js,
and `unzip`. NuGet restores packages from the DotKt feed and nuget.org.
All scripts can be called from any working directory:

```bash
bash scripts/build.sh
bash scripts/verify.sh
bash scripts/pack.sh
node tests/Smoke/verify-lsp.mjs
```

`build.sh` builds the generator. `pack.sh` creates
`artifacts/packages/DotKtX.Experimental.LspSupport.0.9.6.nupkg`, including its
runtime dependencies, MSBuild integration, `LICENSE.txt` and `NOTICE.txt`.
`verify.sh` packs that package, builds the smoke consumer through a
`PackageReference`, runs it and compares stdout with `tests/Smoke/expected.txt`.
It also checks generated workspaces, JAR structure, metadata accounting, receiver
and suspend callback typing, and the plain-Java fallback. Build logs and actual
stdout are saved under `artifacts/verification/`. Test projects are not packable.

Additional arguments are forwarded to `dotnet build` or `dotnet pack`.
For verification, use MSBuild options shared by those commands, for example:

```bash
bash scripts/verify.sh -p:RestoreAdditionalProjectSources=/path/to/local/feed
bash scripts/pack.sh -p:RestoreAdditionalProjectSources=/path/to/local/feed
```

The Node verifier additionally starts an installed JetBrains Kotlin language
server and checks CLR-reference completion, `kotlin.clr` completion, member
completion, and go-to-definition end to end. It also checks receiver and suspend
callbacks, their error diagnostics and return type inference, and confirms that
ordinary callbacks still reject suspend calls. Set `KOTLIN_LSP_SERVER` to a
standalone server executable if the VS Code extension is not installed.

The project, output assembly and NuGet ID use `DotKtX.Experimental.LspSupport`.
Version `0.9.4` distinguishes the renamed assembly from `0.9.3`, whose ID used
`DotKtx`; NuGet treats these IDs as the same package. Existing MSBuild property
names (`DotKtxExperimentalLsp*`) and workspace ownership markers remain compatible.
No sibling repository or optional reference clone is required for building or packing.

Validation on 2026-11-05: Release build, package creation, the full verification
script and all real LSP assertions passed (.NET SDK `10.0.401`, DotKt `0.9.20`,
JetBrains Kotlin VS Code extension `0.0.86`). The DLL assembly name, NuGet ID,
bundled runtime dependencies and license/notice files were checked. Calling the
build script from outside the repository with additional arguments also passed.

Validation on 2026-11-10: the `0.9.6` Release package, full verification script
and all real LSP assertions passed with DotKt `0.9.23`, Kotlin `2.4.21`,
.NET SDK `10.0.401` and JetBrains Kotlin extension `0.0.86`. This includes
completion, navigation, metadata hover, receiver/suspend callback typing and
the negative control for ordinary callbacks.
